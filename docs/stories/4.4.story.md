# Story 4.4 – Add WebSocket Debouncing/Throttling

## Status

Ready for Review

## Story

**As a** system/user,
**I want** WebSocket commands to be debounced/throttled when sent rapidly,
**so that** only the last command in a rapid sequence is executed, preventing excessive network traffic and improving performance.

## Acceptance Criteria

1. AC1: When multiple commands are sent rapidly (within a configurable time window, e.g., 300ms), intermediate commands are ignored
2. AC2: Only the last command in a rapid sequence is executed after the debounce delay expires
3. AC3: Debouncing/throttling is configurable (delay duration can be adjusted)
4. AC4: Commands sent after the debounce delay expires are executed immediately (not debounced)
5. AC5: Existing command execution functionality continues to work unchanged for non-rapid commands
6. AC6: Command history tracking continues to work correctly (only executed commands appear in history)
7. AC7: WebSocket connection status checks remain functional
8. AC8: Error handling for failed commands is preserved

### Implementation Playbook (Dev Agent)

Follow these steps when implementing this story:

1. **Debouncing wrapper in useCommandExecutor**
   - Add debounce logic using `useMemo` and `useCallback` with a timeout
   - Store pending command in a ref to allow cancellation
   - Implement configurable delay (default 300ms, make it optional prop/option)
   - Clear timeout on component unmount

2. **Command history tracking**
   - Only add to history when command is actually sent (not when debounced)
   - Update history status appropriately

3. **Connection and error handling**
   - Ensure debouncing doesn't interfere with connection status checks
   - Preserve existing error handling flow

4. **Testing**
   - Unit tests for debounce logic with rapid sequences
